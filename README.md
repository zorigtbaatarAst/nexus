# BugHunter

*[English](README.en.md) · Монгол*

**Өөрчлөлт мэдэрдэг кодын оюун ухааны систем.** Кодын санг нэг удаа ойлгож, бүтэц болон
алдааны түүхийг нь санаж, скан хооронд юу өөрчлөгдсөнийг илрүүлж, тэр өөрчлөлтийн нөлөөг
тооцоолж, боломжит алдааг олоод — **тестээр давтан үүсгэж баталгаажуулна.**

> **Төлөв: MVP хийгдэж байна.** Архитектур бүрэн бэлэн
> ([`docs/architecture.md`](docs/architecture.md)); суурь араг яс —
> Java хэл дээр `init`, `scan`, `rescan`, `status`, `changes`, `doctor` — ажиллаж байна.
>
> ```
> cargo build --release && make demo REPO=/аль нэг/spring/төсөл
> ```
>
> Давхаргууд хоорондын мөшгөлт аль хэдийн ажиллаж байна (Spring for GraphQL + Apollo):
> backend сервисийн метод өөрчлөгдөхөд түүнийг харуулдаг React компонентууд хүртэл хүрнэ.

## Үндсэн санаа

**BugHunter нотолгоо, түүх, баталгаажуулалтыг хариуцна. AI агент дүгнэлтийг хариуцна.**

Агентад таны бүх репозитор хэрэггүй — түүнд хэрэгтэй нь дөрөвхөн зүйл: эх кодын зөв 4 КБ,
юу өөрчлөгдсөн, тэр өөрчлөлт юуг хөндөж байгаа, мөн тэр газар өмнө нь юу эвдэрч байсан.
Яг үүнийг детерминистик байдлаар, тогтвортой бэлтгэж өгөх нь энэ системийн бүх ажил юм.

Оюун ухаан нь prompt хэлбэртэй биш, **нотолгооны хэлбэртэй** учраас MCP дэмждэг ямар ч
агент үүнийг ашиглаж чадна: Claude Code, Codex, Copilot, эсвэл хараахан гараагүй ямар нэг
хэрэгсэл. Нотолгоо нь детерминистик учраас AI-г бүр мөсөн унтраасан ч BugHunter ажлаа
хийсэн хэвээр байна.

## Хэрхэн ажилладаг вэ

```
bughunter init         хэл, framework, build систем, өгөгдлийн сан, контейнерийг илрүүлнэ
bughunter scan         файл, симбол, хамаарал, тестийг индексжүүлж → суурь тогтооно
bughunter rescan       суурьтай харьцуулж → өөрчлөгдсөн симбол → нөлөө → алдаа хайх
bughunter impact       симбол/файл/нэрийн нөлөөллийн хүрээ — давхаргууд дамжина
bughunter graph        хамаарлын графын хэмжээ ба хэдэн хувь нь тодорхойлогдсон
bughunter investigate  дэлгэцийн зураг → UI холбоос → давхаргын заагийг давж → сэжигтнүүд
bughunter verify       давтан үүсгэх тест бичиж, ажиллуулж, суурь дээр дахин шалгаж дүгнэнэ
```

### Хоёр эхлэх цэг

`rescan` нь **"энэ коммит юуг эвдсэн бэ"** гэсэн асуултад хариулна.

`investigate` нь алдаа бодит амьдрал дээр хэрхэн ирдэг тэр замаар ажиллана — хүн дэлгэц рүү
заагаад *"энэ тоо буруу байна"* гэж хэлэхэд. BugHunter тэр шинж тэмдгийг компонент дээр
холбож, frontend болон backend хоёрын **HTTP заагийг давж**, repository-ийн метод хүртэл
мөшгөөд сэжигтнүүдийг эрэмбэлнэ.

**Дэлгэцийн зургийг агент уншина, BugHunter хэзээ ч хүлээж авахгүй.** Агент зурган дээрээс
ажиглалт (маршрут, харагдаж буй текст, network хүсэлт, console алдаа) гаргаж өгнө; BugHunter
тэдгээрийг өөрийн индекс дээр детерминистик байдлаар холбоно. Харагдах чадвар бол дүгнэлт,
дүгнэлт нь агентын ажил.

Бүх репозиторыг уншдаг цорын ганц ажиллагаа бол эхний скан. Дараагийн скан бүр нь
**байгаа кодын хэмжээгээр биш, өөрчлөгдсөн хэсгийн хэмжээгээр** зардал гаргана: 5 сая мөр
кодтой monorepo дээр өөрчлөлтгүй `rescan` хоёр секундээс доош байхаар зорьсон.

## Зохиомжийн зарчим

1. **Детерминистик нотолгоо нь AI-н таамгаас давуу.** Шалгаж болох `file:line` нотолгоогүй
   олдвор бол хадгалагдахгүй, хилийн шатанд шууд буцаагдана.
2. **AI бол сонголт.** Детерминистик build-д HTTP client огт байхгүй — амлалт биш,
   `cargo tree`-ээр шалгаж болох шинж чанар.
3. **Репозиторыг хаашаа ч бүтнээр нь илгээхгүй.** Контекст гэдэг нь эрэмбэлэгдсэн,
   токены хязгаартай нотолгооны багц бөгөөд "файлыг бүтнээр нь оруулъя" гэсэн зам байхгүй.
4. **Продакшн кодыг өөрчлөхгүй.** Үүсгэсэн тестүүд тусгаарлагдсан хавтаст амьдарна;
   хөгжүүлэгчийн ажлын мод хэзээ ч checkout, stash, reset хийгдэхгүй.
5. **Алдаа чимээгүй өнгөрөхгүй.** Задлан шинжлэхэд алдсан файлыг тэмдэглэж, тайлагнана;
   тасалдсан үр дүн нь тасалдсанаа хэлнэ; суурь коммит олдохгүй бол бүтэн скан руу
   шилжээд **тэрийгээ хэлнэ**.
6. **`FIXED` төлөвт нотолгоо шаардана.** Хэсэгчилсэн скан дээр алдаа харагдаагүй нь тэр
   хэсгийг шалгаагүй гэсэн үг — засагдсан гэсэн үг биш.
7. **Таамаглахгүй, асууна.** Даалгавар бүрэн бус эсвэл ойлгомжгүй байвал ямар ч tool нь
   тодорхой асуултуудыг — тус бүрдээ *яагаад* асууж байгаа шалтгаантайгаар — буцаана.
   Дөрвөн боломжит компонентоос нэгийг нь чимээгүйхэн сонгоод итгэлтэй дуугарах нь
   хамгийн муу хувилбар: хэн ч түүнийг таамаг байсныг мэдэхгүй өнгөрнө.

## Жишээ: дэлгэцийн зургаас алдаа хүртэл

```
хүн → агент     [дэлгэцийн зураг] "Сагсны нийт дүн 0 харагдаж байна, гэтэл 3 бараа байна"

агент → bughunter_investigate { route: "/checkout",
                                visible_text: ["Нийт дүн", "0 ₮"],
                                network: [{ method:"GET", path:"/api/cart", status:200 }] }

  ← ТОДРУУЛГА ШААРДЛАГАТАЙ
    энэ маршрут дээр 4 компонент нийт дүн харуулдаг
    асуулт: "Аль хэсэг нь буруу тоо харуулж байна — барааны жагсаалт уу,
             эсвэл доод талын нийлбэрийн хэсэг үү?"
    яагаад: "Хоёулаа нийт дүн харуулдаг бөгөөд өөр өөр endpoint дуудаж байна."

хүн → "доод талын нийлбэрийн хэсэг"

  ← МӨШГӨЛТ
    TotalsPanel → useCart() →[calls_http GET /api/cart/:p]→ CartController#get
                → CartService#totals → CartRepository#findItems → cart_items

  ← СЭЖИГТНҮҮД
    1. CartService#totals        0.81   мөшгөлт дээр байна · өчигдөр өөрчлөгдсөн · тестгүй
    2. CartDto.totalAmount       0.74   ГЭРЭЭНИЙ ЗӨРҮҮ
       backend `total_amount` гэж илгээж байхад TotalsPanel.tsx:34 нь `totalAmount`
       гэж уншиж байна → undefined → 0 гэж харуулна

  ← ОЛДВОР  BUG-118 · api-contract · confidence 0.90
```

Хоёрдугаар сэжигтнийг **ямар ч AI загвар оролцоогүйгээр** оллоо. Хоёр талын талбарын нэр
зөрж байгаа, хоёулаа индекслэгдсэн — тэднийг харьцуулах нь зүгээр л join хийх ажил.
Агентын дүгнэлтийг үнэхээр шаардлагатай хэсэгт нь зарцуулах боломж ингэж гарна.

## Одоогийн байдал

| Crate | Төлөв |
|---|---|
| `bh-types` · `bh-store` · `bh-vcs` · `bh-lang` · `bh-lang-java` · `bh-lang-ts` · `bh-core` · `bh-cli` | ажиллаж байна |
| `bh-lang-python` · `bh-lang-rust` · `bh-verify` · `bh-ai` · `bh-mcp` | V1 |

Өгөгдлийн сан нь эхний өдрөөс **бүрэн 21 хүснэгтийн схемтэй**. Алдаа болон
баталгаажуулалтын хүснэгтүүдийг дараа нэмбэл дүүрсэн сан дээр migration хийх шаардлагатай
болох тул шууд бүтнээр нь тавьсан.

Жинхэнэ 880 файлтай Spring + Next.js төсөл дээр: 5,665 симбол, төслийн дотоод хамаарлын
**96% нь тодорхойлогдсон**, 641 мс. Үүний 402 нь GraphQL заагийг давсан `contract` ирмэг.

109 файлтай Spring Boot төсөл дээр: бүтэн скан 32 мс / 939 симбол, өөрчлөлтгүй `rescan`
3 мс, нэг методын бие засварласан тохиолдолд 5 мс.

```
$ bughunter impact 'mn.autoland.sales.vehicle.service.VehicleService#list' --paths

  0.81  VehicleGraphQLController#vehicles(...)
  0.57  graphql:Query.vehicles
  0.46  graphql:op:Vehicles
  0.37  frontend/src/app/(sales)/vehicles/page#VehiclesPage
```

Java методын нэг мөр өөрчлөхөд ямар React компонентууд эвдэрч болохыг харуулж байна.

**Хамгийн чухал баталгаа:** бүх 109 файлыг дахин форматласны дараа (диск дээр 14,000 мөр
өөрчлөгдсөн) `rescan` нь **0 симбол өөрчлөгдсөн** гэж хариулна. Ингэснээр `spotlessApply`
ажиллуулах бүрт алдаа хайх процесс дэмий эхлэхгүй.

## Төлөвлөсөн технологи

Rust · Cargo workspace · нэг статик binary · SQLite (WAL) · tree-sitter · git2 · rmcp · clap.

Java, TypeScript, Python, Rust хэлний задлан шинжлэгчид нь `LanguageAnalyzer` интерфейсийн
ард байрлана. Framework мэдлэг (Spring, NestJS, Next.js, Django) нь тусдаа өргөтгөлийн цэг —
учир нь Spring гэдэг Java биш, мөн DI хэлбэрийн уялдаа өөр хэлүүдэд бас давтагдана.

Frontend болон backend хоёрыг холбох заагийг **HTTP гэрээ** дээр хийнэ: хоёр талыг
`METHOD /path/:p` гэсэн нэгдсэн хэлбэрт хөрвүүлж тааруулна. Ингэснээр гүйлгээ ажиллуулах,
instrumentation хийх, эсвэл нийтлэг схем шаардахгүйгээр UI дээрх шинж тэмдгээс өгөгдлийн
сангийн хүснэгт хүртэл мөшгих боломжтой болно.

Хэл сонгосон үндэслэл, татгалзсан гурван хувилбар:
[ADR-001](docs/architecture-decisions.md#adr-001-rust-for-bughunter-core).
