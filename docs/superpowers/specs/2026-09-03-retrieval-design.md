# Retrieval — Design

**Status:** approved, not yet implemented
**Date:** 2026-09-03
**Absorbs** [`2026-09-03-knowledge-selectivity-design.md`](2026-09-03-knowledge-selectivity-design.md),
whose durable-facts change is a prerequisite here. That document stays as the record of what
was measured about graphify's prose; this one is what gets built.

## Why

Three questions were asked of this architecture. Each was measured rather than argued.

### Does the architecture need an update?

Not a rewrite. The crate boundaries hold and `crates/nexus-cli/tests/boundaries.rs` enforces
them. Two structural problems, both in retrieval, both below.

### Can memory be more efficient?

Every context request loads **every live fact** and ranks them in Rust:

```rust
crate::memory::rank(self.store.facts(self.project_id, None)?, &relevant, current_scan)
```

Measured on a clone of this repository, package cache cleared before each run:

| Live facts | `nexus context --task`, median of 5 |
|---:|---:|
| 0 | 14 ms |
| 1,000 | 15 ms |
| 10,000 | 28 ms |
| 50,000 | 72 ms |
| 200,000 | 274 ms |

Linear in total memory, and memory is append-only by design — §3 invalidates, it does not
delete. [ADR-024](../../architecture/decisions/ADR-024-hooks-are-the-invocation-tier-and-ship-off-by-default.md)
budgets **150 ms** for a per-prompt hook; that is crossed near 100,000 facts.

`idx_facts_subject` on `(project_id, subject) WHERE invalidated_at IS NULL` has existed since
`0001_init.sql`. The hot path never uses it, because it passes `subject = None`.

### Is bug fixing actually more efficient?

For the scan and review moments, yes. For **debugging**, no. Four real defects fixed in this
repository on 2026-09-03, each given to `nexus context --task` as its symptom:

| Symptom given | Cause was in | Result |
|---|---|---|
| `context --task 'refactor normalize_body'` returns an empty package | `context/seeds.rs` | miss — returned the three analyzers |
| `tokens_estimated` says 253 but the package ships 11,113 tokens | `engine/query.rs` | **0 items** |
| the context cache serves a package from before a fact was recorded | `context/cache.rs` | **0 items** |
| resolved call edges fell from 551 to 104 after a rename | `nexus-store/src/lib.rs` | **0 items** |

Zero for four. Three separate causes:

1. **The seed filter skips plain lowercase words.** `cache` is indexed as
   `nexus_core::context::cache`, but `seeds::targets` accepts a word only if it carries a
   capital, `_`, `::`, `.`, `/` or `#`. A symptom is written in plain words.
2. **A symptom names where a defect shows, not where it lives.** `normalize_body` correctly
   seeded the three analyzers; the defect was in the seed stage. No retrieval design fixes
   this one — it is why a human still debugs.
3. **Symptom-driven investigation is documented and not built.** `docs/investigation.md`
   describes screenshot → suspect and `README` links it; `SymptomReport` appears nowhere in
   `crates/`.

This design addresses (1). (2) is inherent. (3) is out of scope and named as such below.

## Design

### 1 — Retrieval asks SQL for the facts that could match

`memory::subject_match` defines a match: exact subject (1.0), or either string a prefix of the
other (0.6), else 0.0 floored to 0.3 — and the task path keeps a fact only when the score
exceeds 0.3. That predicate is pushed into SQL.

New store method:

```rust
pub fn facts_for_seeds(&self, project_id: ProjectId, seeds: &[String]) -> Result<Vec<FactRow>>
```

Two arms, both riding `idx_facts_subject`:

| Arm | SQL | Covers |
|---|---|---|
| exact | `subject IN (<seeds and every prefix of each>)` | `subject == seed`, and a fact about an ancestor module of the seed |
| descendant | per seed, `subject >= seed AND subject < seed \|\| X'10FFFF'` | a fact about something deeper than the seed |

A prefix set is generated by splitting each seed on `::`, `.` and `#` — at most about six per
seed, **deduplicated**, which collapses hard in practice because every seed under
`nexus_core::context` contributes the same two ancestors. The descendant arm is written as a
half-open range rather than `LIKE seed || '%'` because a range on an indexed column is an
index seek and `LIKE` with a bound parameter is not guaranteed to be.

Bound parameters stay well inside SQLite's limit: 256 seeds with deduplicated prefixes is a
few hundred values, against a `SQLITE_MAX_VARIABLE_NUMBER` of 32,766 in the bundled SQLite
3.53. The count is asserted by a test rather than assumed, because the failure mode of
exceeding it is a runtime error on a large project and never on a fixture.

**The seed set is capped at 256** (`SEED_QUERY_CAP`), taking seeds before expansion items in
their existing order. Expansion has `max_depth: 5` and no node cap; a four-symbol prompt on
this repository already reaches 189. When the cap bites, the package `notes` says so — §5's
principle is that errors never pass silently, and a silently narrowed query is an error.

The Rust-side `to_seeds <= 0.3` filter **stays**. It remains the single definition of a match;
it simply stops being the only one. Two rankings over one table would eventually disagree, and
the one further from the data would be the wrong one.

`Engine::session_package` stops calling `facts(…, None)` as well. It takes durable facts only,
riding `idx_facts_state` — the change specified in the selectivity design, required here
because otherwise the session path keeps the unbounded scan this section exists to remove.

`Engine::memory_export` keeps loading everything. Its job is everything, and it is a batch
command, not a hook path.

### 2 — A symptom can seed a package

`seeds::targets` gains plain lowercase words: **≥ 4 characters, not a stopword**, and accepted
only if the word resolves to **exactly one** indexed symbol whose own last segment equals the
word.

That uniqueness rule already exists. `Engine::symbol_named_in`, added for the graphify import,
applies it for the same reason: `find_symbols` matches by suffix, which is right for a name a
person typed and wrong for prose, where "integration" once anchored six design claims on
`NoContinuousIntegration`. The two callers share one function; it moves to
`context::seeds` and the importer calls it.

**No intent gate.** The widening applies to every request. Gating on the verb table adds a
branch that will misclassify sometimes, and a widening that silently fails to happen is the
hardest kind of defect to notice. The uniqueness rule is the noise control, and it does not
care what the verb was.

**The stopword list is a `const` in `seeds.rs`**, next to `targets`. The Rust analyzer's
PRELUDE deny-list already solved this exact shape of problem in the same way: greppable,
versioned with the code, one place to change. It holds English function words and the code
words a prompt uses about code rather than as code — `test`, `error`, `value`, `result`,
`file`, `line`, `call`, `type`, `data`, `code`, `name`, `case`, `item`, `list`, `null`.

**Cost, measured.** A word that passes the filter is one indexed lookup. Timed on this
repository: 3 target words 12 ms, 40 target words 23 ms — about **0.3 ms per lookup**. A
25-word symptom adds roughly 7 ms. The comment in `seeds.rs` justifying the narrow filter
("a handful of indexed lookups instead of one per token, which is what ADR-024's 150 ms budget
for a per-prompt hook can afford") is over-cautious by an order of magnitude, and is replaced
with the measurement.

### 3 — Knowledge selectivity

As specified in the absorbed document, unchanged:

- Import a graphify prose node only when it is a `rationale`, a `concept` something is a
  `rationale_for`, a `concept` whose label reads as a sentence, or a `concept` that names an
  indexed symbol — and never from `tests/` or a `/blobs/` path. 681 → about 427.
- `session_package` carries durable facts. An imported claim earns its place by surviving
  three scans; it does not buy session budget on arrival.
- Task packages keep candidates, deliberately.

## Consequences

| | Now | After |
|---|---|---|
| Task package, 10,000 unrelated facts | 28 ms | flat at ~14 ms |
| Task package, 200,000 unrelated facts | 274 ms | flat at ~14 ms |
| Session package, fresh graphify import | 752 tokens, 9 alphabetical claims | ~194 tokens |
| `the context cache serves a stale package` | 0 items | anchored on `nexus_core::context::cache` |
| A 25-word symptom | ~14 ms | ~21 ms |

**Golden packages will move.** The widening applies to every request, so a golden task whose
text contains a plain lowercase word naming exactly one symbol gains a seed. That is the
change working. Rebaseline with `NEXUS_REBASELINE=1` and read the diff before accepting it.

## Acceptance criteria

1. Recording 10,000 facts about symbols unrelated to the request leaves a task package's
   `items_considered` unchanged, and its latency within 20% of the same request at zero facts.
2. A fact whose subject is an ancestor module of a seed is still retrieved; so is one about a
   symbol deeper than a seed. Both are asserted against a real index, not a mock.
3. With more than `SEED_QUERY_CAP` relevant symbols, the package `notes` says the seed set was
   capped.
4. `nexus context --task "the context cache serves a package from before a fact was recorded"`
   returns an item anchored in `crates/nexus-core/src/context/cache.rs`. The four symptoms in
   the table above are the regression fixture, each with its known answer file.
5. A plain word matching two or more symbols seeds nothing, and a stopword seeds nothing.
6. `symbol_named_in` has one definition, used by both the seed stage and the graphify import.
7. The session package contains no non-durable fact; a fact with `validated_count >= 3` or
   `source = 'human'` does appear in it.
8. A graphify node labelled `next` or `Golden Fixture Repositories` is not imported; one
   labelled `Budget is selection, not truncation` is.
9. `make check` green. Golden packages rebaselined with the diff inspected.

## Out of scope, and named

**Symptom → suspect as a subsystem.** `docs/investigation.md` describes an entry point that
takes a screenshot or a stack trace and produces ranked suspects. Nothing implements it. This
design makes a symptom *sentence* able to seed a package; it does not build the investigation
entry point, and the documentation should not be read as describing shipped behaviour until it
does.

**Matching error text and log lines.** A symptom often quotes a string literal from the source
("no such column: lang"). Source string literals are not indexed — `ui_strings` indexes i18n
values, which is a different thing. Indexing them is a real lead and a separate change.

**BugHunter's detector coverage.** Three detectors ship: `spring`, `graphql`, `secrets`. Two
are Java/JS-only, so on a Rust project only the secrets rule can fire. That is a capability
question, not a retrieval one.

**Cause versus symptom.** No retrieval design closes the gap between where a defect shows and
where it lives. `normalize_body` correctly seeded the three analyzers while the defect sat in
the seed stage. That is what the human is for.
